## خلاصه‌ی مدیریتی

### ۱. مهم‌ترین یافته: نشت اطلاعات در ریپوی عمومی (🔴)
پوشه‌ی `scratch/` با اینکه در `.gitignore` آمده، **قبلاً commit شده** و الان در ریپوی عمومی است. داخلش:
- پسورد **root** چند سرور (در حدود ۴۰ اسکریپت paramiko)،
- **توکن ربات تلگرام**، یوزر/پسورد MySQL ربات و `backup_secure_token` (فایل `remote_global_config.php`)،
- **API Key پنل WGDashboard** که ربات با آن کار می‌کند (`bot_marzban_panel_dump.txt`)،
- **کلید خصوصی سرور WireGuard (اینترفیس)** — ۱۶۱۶ بار در `bot_user_info_dump.txt`،
- کلیدهای خصوصی و PSK تمام کاربران، هش پسورد ادمین‌های ربات، پسورد ادمین پنل.

با API Key افشاشده هر کسی می‌تواند از طریق `PostUp` یک کانفیگ، **دسترسی root روی سرور** بگیرد. جزئیات و ترتیب اقدام در [سند ۰۱](01-URGENT-Leaked-Secrets.md).

### ۲. Total Usage اینترفیس (سؤال شما)
اصلاحیه‌ی Antigravity **در اصل درست کار می‌کند**: حذف peer، ریست مصرف و restrict دیگر از Total Usage کم نمی‌کنند (جدول `*_traffic_snapshot`). ولی ۳ اشکال واقعی دارد:
1. در حذف peer، اگر `total_data` آن peer صفر باشد (مثلاً بعد از ریبوت سرور و بدون مصرف جدید)، مصرف تجمعی‌اش **دو بار** به Total اضافه می‌شود ← Total بیشتر از مقدار واقعی و `Total ≠ Sent + Receive`.
2. ریستور بکاپِ یک کانفیگ (Backup per-configuration) به‌خاطر یک تغییر در commit `5dbe527` **همیشه شکست می‌خورد** و اینترفیس را خاموش رها می‌کند.
3. مصرف کاربرانی که **قبل از** این اصلاحیه حذف شده‌اند برنمی‌گردد (باید دستی وارد شود).

جزئیات، سناریوها و کوئری‌های SQL برای بررسی روی سرور در [سند ۰۴](04-Total-Usage-Review.md).

### ۳. ارتباط ربات (OxBot) با پنل
- **باگ وضعیت:** API پنل، peerهای restrict‌شده را **دو بار** برمی‌گرداند (یک بار در `configurationPeers` و یک بار در `configurationRestrictedPeers`). ربات اولی را پیدا می‌کند و کاربر غیرفعال را «فعال» می‌بیند. دکمه‌ی فعال/غیرفعال ربات برای این کاربران کار نمی‌کند. همین باعث **نمایش تکراری** peerها در UI پنل هم شده.
- **باگ مالی در ربات:** خرید «حجم اضافه» بعد از تمام شدن حجم، مصرف را **ریست** می‌کند ← کاربر حجم قبلی را رایگان دوباره می‌گیرد. خرید «زمان اضافه» برای کاربری که حجمش تمام شده، دسترسی را بدون محدودیت حجم باز می‌کند.
- **فریز پنل:** ربات برای هر کار روی هر کاربر کل لیست peerها (چند مگابایت JSON) را می‌گیرد. در کرون‌ها این بار از مرتبه‌ی N² است.
- **job ها شکننده‌اند:** یک job با مقدار نامعتبر کل سیستم job را از کار می‌اندازد و job هایی که ۱۱ بار شکست بخورند بی‌صدا پاک می‌شوند ← کاربر **نامحدود** می‌ماند.

جزئیات در [سند ۰۶](06-OxBot-Integration.md).

### ۴. Global Backup
ریستور، فایل SQLite را **حین کار** برنامه پاک و بازسازی می‌کند، در حالی که threadهای پس‌زمینه همچنان روی دیتابیس می‌نویسند. این یکی از محتمل‌ترین ریشه‌های خطاهای `database disk image is malformed` است. هش‌های MANIFEST هم هیچ‌وقت بررسی نمی‌شوند و فایل بکاپ آپلودی می‌تواند `gunicorn.conf.py` و پلاگین‌ها را بازنویسی کند (اجرای کد به‌عنوان root). جزئیات در [سند ۰۵](05-Global-Backup-Review.md).

### ۵. «Auto-heal» کلیدها: یک ریسک پنهان بزرگ
اگر به هر دلیلی (ریستور، دیتابیس جدید، مهاجرت سرور، self-heal دیتابیس، ویرایش raw کانفیگ) peerهایی در فایل `.conf` باشند ولی در دیتابیس نباشند، پنل **کلید همه‌ی آن‌ها را عوض می‌کند** (`healPeersWithMissingPrivateKeys`). کلاینت‌های واقعی دیگر وصل نمی‌شوند و ربات هم دیگر آن‌ها را پیدا نمی‌کند. جزئیات در [BUG-03](03-Backend-Bugs-and-Logic.md#bug-03).
